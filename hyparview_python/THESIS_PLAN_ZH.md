# 本科研究方案：Capacity Adaptive Membership Overlays for Heterogeneous Distributed Systems

本课题研究一个具体问题：**在节点 CPU 和 RAM 配置已知、通信理想的条件下，能否通过调整 HyParView 的 active view 上限，让较强节点承担更多连接与转发工作，同时维持可接受的连通性和故障恢复能力？**

本项目不采集 CPU 利用率或内存占用，不实现资源监控器，不模拟随机丢包和网络时延。CPU 与 RAM 是实验输入；Memory 在这里就是 RAM，不作为另一个资源重复加权。结果首先说明所定义仿真模型中的行为，不能直接解释为真实机器的吞吐提升。

## 1. 研究问题与预期贡献

| 研究问题 | 需要观察的证据 |
|---|---|
| RQ1：资源相关的连接上限是否产生预期的实际度数分配？ | capacity 与 degree、上限占用率；强节点是否确实承担更多连接 |
| RQ2：它是否降低弱节点相对能力的转发负担？ | 各能力组应用发送次数及每广播平均发送次数 / capacity；与固定上限和错误匹配对照比较 |
| RQ3：已知资源配置变化后，局部调整能否重新分配连接？ | adaptive 与 static 的相同初始拓扑、变化后 degree 和连接变更开销 |
| RQ4：这种分配在随机失败和高能力节点失败下有什么代价？ | 故障后广播可靠性、连通分量、失效条目和恢复控制开销 |

本科范围的贡献是：一个明确的资源到连接预算的启发式、在现有协议中的实现、包含消融对照的评估，以及对适用条件和失败情形的解释。不要求证明最优性，也不要求提出全新的 gossip 协议。

## 2. 文献依据与本研究自己的选择

**论文事实：**HyParView 使用小型双向 active view 和较大的 passive view；前者用于广播，后者提供故障替补。原论文 §6 已将考虑节点异构性、调整 fanout / degree 列为未来工作。因此本课题可以实现并评价这一方向，不能声称首次提出 capacity-aware overlay。[HyParView 作者会议版，§4、§6](https://joaoleitao.org/pdf/HyParView.pdf)

**论文事实：**Gia 让较强节点拥有更多连接，并结合搜索、流控和内容索引。其 capacity 表示查询处理能力；原型 §5.1 实际按接入带宽配置，没有给出 CPU/RAM 到度数的公式。它提供异构拓扑的动机，不能作为本研究资源公式的直接出处，也不能将 Gia 的整体性能提升归因于单独改变连接上限。[Gia 作者论文，§3、§5.1](https://people.eecs.berkeley.edu/~sylvia/papers/1103-chawathe.pdf)

下文的 CPU/RAM 评分、对数映射、上下限、动态交换、实验窗口及公平性对照均为**本研究的设计选择**。HyParView 的论文规则与当前仿真调度边界另见 [PROTOCOL_SPEC_ZH.md](PROTOCOL_SPEC_ZH.md)。

## 3. 最小算法

### 3.0 为什么只用 CPU 和 RAM，以及可以怎样扩展

资源值是**已知输入**（例如云主机规格、容器的 `cpus` / `memory` 配额，或部署清单），如何测量不在本文范围内。论文中只需写明：“节点在加入时以本地配置的形式得知自身 CPU 与 RAM；本文不讨论资源测量或资源申报的真实性。”

| 候选因素 | 本文处理 | 理由 |
|---|---|---|
| CPU（核数或可比较的 CPU 单位） | 使用 | 转发与连接管理的处理能力代理 |
| RAM（GiB） | 使用 | 维持连接、缓冲与视图状态的能力代理 |
| 网络带宽 | 不纳入主模型，在讨论中列为最重要的扩展 | 洪泛广播的发送成本主要落在上行带宽上；Gia 实际按带宽配置 capacity。纳入它需要链路或服务率模型，超出理想仿真 |
| 磁盘、GPU | 不使用 | 与 membership overlay 的工作无直接关系 |
| 实时负载 / 利用率 | 不使用 | 需要测量与平滑，属于监控问题；本文的动态实验只模拟“已知配置发生变化” |
| 在线时长 / 稳定性 | 不使用，可作为未来工作 | 与故障概率有关，但需要 churn 模型 |

建议在论文中明确：取 `min` 意味着**瓶颈资源决定 capacity**。只要协议只看到 c，CPU 与 RAM 的具体组合不会改变结果（见 §8 的 decoupled 不变性检查）。若要研究 CPU 与 RAM 各自的作用，需要换**评分函数**（例如加权几何平均 \(c=(CPU/2)^{w}(RAM/4)^{1-w}\)）并比较不同 w，而不只是换输入分布。

### 3.1 从已知资源得到 capacity score

对节点 i，定义：

\[
c_i=\min\left(\frac{CPU_i}{2},\frac{RAM_i\;(GiB)}{4}\right).
\]

CPU 与 RAM 都必须为正数。2 个 CPU 核和 4 GiB RAM 是参考配置；两个比值均无量纲。取最小值表达“某一资源较弱时形成瓶颈”的模型假设。它不是实际查询率、吞吐或经过测量的 CPU 处理能力。

### 3.2 从 score 得到 active 上限

\[
k_i=\operatorname{clip}\left(
\left\lfloor3+2\log_2(c_i)+0.5\right\rfloor,\;3,\;9\right).
\]

其中 clip 将结果限制在 [3, 9]。`floor(x + 0.5)` 明确规定整数舍入，避免依赖不同语言的默认 round 行为。对数映射使配置翻倍时增加少量连接，避免连接上限随资源值无限增长；3 和 9 是本研究参数，不是论文推导出的最优值。

| 资源组 | CPU 核 | RAM GiB | c | k |
|---|---:|---:|---:|---:|
| low | 2 | 4 | 1 | 3 |
| medium | 4 | 8 | 2 | 5 |
| high | 8 | 16 | 4 | 7 |

三组等比例时，连接上限总预算为：

\[
B=\sum_i k_i=\frac N3(3+5+7)=5N.
\]

这与所有节点上限为 5 的固定方案匹配。它匹配的是**允许的连接槽位总数**，不是保证形成相同数量的真实边。上限不是实际 degree；候选不足或对端拒绝时，节点可以低于上限。

该映射不是 capacity 比例分配。例如三组的 k/c 为 3、2.5、1.75，并不相同。因此不要将方案命名为“严格按能力比例分摊工作量”。

### 3.3 保持其余协议机制一致

- 保留原有随机 JOIN / FORWARD_JOIN、passive shuffle、双向连接和邻居优先级规则。
- 修复时仍随机遍历有限 passive 候选，不增加偏向高能力节点的选邻居规则。
- 使用现有 `Node.set_active_size`：缩容随机断开多余连接，扩容排队进行一次本地修复扫描。
- 不周期性强制填满 active；维护使用 `fill=False`。候选不足、拒绝或度数未满均保留并测量。

这样可将主要变化限定为“连接上限如何分配”，避免把路由、流控、资源评分和拓扑偏好同时改动。

共同参数保持 `passive_size=30`、`arwl=6`、`prwl=3`、`k_a=3`、`k_p=4`、`shuffle_ttl=6`。其中 shuffle TTL=6 是本项目已明确记录的配置选择。各方案不得通过额外扩大 passive 或提高 shuffle 频率获得未说明的优势。

## 4. 三个稳定比较方案

| 方案 | active 上限 | 目的 |
|---|---|---|
| fixed-5 | 每节点 5 | 固定 HyParView baseline |
| static-capacity | 按实际资源映射为 3 / 5 / 7 | 评价能力相关上限 |
| permuted-caps | 保留完全相同的 3 / 5 / 7 上限集合，随机分配给节点，使其与资源错配 | 区分异构上限本身与“上限匹配资源”的作用 |

permuted-caps 只打乱上限，不打乱用于计算工作量归一化指标的真实资源。保存每个节点的资源、score、上限和 permutation，便于核查。

三者使用相同节点资源、加入顺序、联系人、广播源、故障名单及其余协议参数。协议随机源与生成这些外部事件的随机源分开。相同 seed 是可复现的入口，但不同算法可能消费不同数量的随机数，不能据此宣称它们经历了完全相同的内部随机过程。

## 5. 动态实验：已知配置变化，不做监控

动态实验单独比较两份**初始资源、上限和拓扑完全一致**的 static-capacity 与 adaptive 运行，先验证变化前的图确实一致。

资源变化可理解为虚拟机 / 容器的 CPU 与 RAM 配额被重新配置；输入直接给定，不需要模拟物理硬件更换或实现监控程序。

1. 三资源组等比例加入并稳定。
2. 从 low 组和 high 组各选总节点数的 10%，两两交换完整的 CPU/RAM 配置。实现中取 m=max(1, floor(0.1N))，并限制不超过任一组的大小；两组各选 m 个。N=120 时各选 12 个，共改变 24 个节点。保存交换配对；medium 不变。
3. static 冻结旧上限；adaptive 按交换后的已知资源重新计算上限。
4. adaptive 先对所有需要缩容的节点调用 `set_active_size`，再处理所有扩容节点，之后统一调用一次 `drain()`。批量缩容在先，避免不同节点遍历顺序把临时资源竞争引入比较。
5. 记录配置变化前、这次 drain 后，以及后续维护轮次的 degree、目标占用率和控制开销。后续 `tick` 仍为 `fill=False`。

成对交换保持资源与上限的整体分布不变，adaptive 的总预算仍为 5N；static 的总预算也不变。变化后 static 的上限可能与新资源不匹配，这正是动态对照。

变化后工作量必须除以**变化后的** c，不能继续用旧资源归一化。这里只模拟外部告知配置变化，不模拟发现配置变化的监控成本。一次局部修复没有达到新上限，也属于结果，不能用全局搜索或强制补边掩盖。

动态运行包含两个独立的工作量测量窗口：预热结束后、资源变化前发送 m 次广播并记录 `before`；最后一个维护 tick 后再发送 m 次广播并记录 `final`。pilot 中 m=20，两个窗口分别计算应用与控制计数增量。`broadcast` 会处理待执行的本地修复，因此测量本身可能推进协议；`final` 是最后广播窗口结束后的状态，不等于 `history` 最后一个 tick 的只读快照。该窗口的控制工作保存在 `window_control_attempts`；时间线按 tick 和 cycle 0 事件操作记录，两者分别解释。

## 6. Failure detection 与故障实验

### 6.1 主实验的检测模型

主设置使用 `on_send`：节点在本地发送、连接尝试或显式 probe 失败时，发现已知地址不可达。注入 crash 不立刻从其它节点视图全局删除失效地址。失败触发现有局部修复；模型不包含超时秒数、误判、随机丢包或网络时延。

`connection` 可作为后续敏感性设置：为已经建立的 active 连接生成本地断裂回调。不能把两种 detector 的结果混在同一统计组；主比较全部使用 on_send。这里评价的是检测事件之后的拓扑与恢复过程，不是现实网络中的检测延迟。

两种 detector 对应原论文中 “TCP 作为不可靠故障检测器” 的两个极端：

| 设置 | 含义 | 何时发现故障 | 运行方式 |
|---|---|---|---|
| `on_send`（主设置） | 仅在发送、连接尝试或 probe 失败时发现 | 懒惰：第一次使用该邻居时 | 默认 |
| `connection`（敏感性） | crash 立即在其所有 active 邻居上产生本地断连事件 | 即时：类似 TCP 连接被对端关闭 | `--failure-detection connection` |

真实系统位于两者之间（取决于 TCP keepalive / 心跳超时）。只要报告两者，就能界定 detector 对结论的影响，无需为本科论文实现超时或误判模型。pilot 显示：在 `connection` 下所有故障场景的广播覆盖都是 100%，因此 `on_send` 下 static-capacity 在高容量定向失败时的覆盖下降，主要来自**尚未被发现的失效 active 连接**（检测滞后），而不是持久分区；第一个恢复 tick 后最大分量都恢复到 100%。论文中应把这一点写清楚。

### 6.2 每次故障运行的流程

故障实验使用三个稳定方案；每个故障场景从**新建并稳定的 overlay** 开始，不将 20%、50%、80% 失败连续叠加到同一个图上。

1. 顺序加入节点；使用 30 个稳定轮次作为 pilot 设置，记录故障前图、上限预算和计数。主实验可将稳定窗口增加到 50 轮，并检查指标是否稳定。
2. 按场景同时 crash 0%、20%、50% 或 80% 节点。
3. 从预先生成的相同存活源序列执行 20 次 `broadcast`；期间不运行 tick，让发送触发 reactive recovery。
4. 再执行 10 个恢复 tick：`probe_active=True, fill=False`，每轮记录图与控制开销。该阶段额外启用理想探测，与前面的纯广播阶段分别解释。

20 次广播与 10 个恢复 tick 是 pilot 观察窗口，不是论文原实验的完整复现。若窗口结束仍未恢复，应报告未恢复，不将最后一轮强行记作恢复时间。恢复阶段的连通性测量不等同于论文“平均广播可靠性恢复到故障前水平”的 healing time。

### 6.3 两种失败名单

- **random：**从全部节点中随机选取相同比例。
- **top-capacity：**按输入资源计算的 c 由高到低选择；同分时用固定随机规则打破并列。三方案使用相同节点名单。这里按真实资源评分，不按 permuted-caps 中错误分配的上限，也不按实际 degree 排序。

0% 是无故障控制，random 与 top-capacity 在此等价，不把重复标签当成新实验。

故障前 B=5N。相同节点失败后，三方案的**幸存节点上限预算和剩余边数可能不同**，尤其在定向失败时。必须同时报告：失败节点数、失去的 capacity、幸存预算、幸存边数和有效平均 degree。不能只用“删除了相同比例节点”宣称故障后的资源预算完全公平。

## 7. 指标与公式

令 V 为当前存活节点集合，n=|V|，d_i 为节点在存活双向 active 图中的 degree；m 为测量窗口内的广播次数，pilot 中 m=20。所有应用与控制消息指标应按阶段取计数增量，避免把加入和稳定过程累计成本混入故障恢复成本。

| 指标 | 定义 | 应如何解释 |
|---|---|---|
| 连接预算 | B=Σ k_i | 配置允许的槽位数量 |
| 实际边数 | E=½Σ d_i | 真实形成的连接；用于检查预算是否实际利用 |
| 目标占用率 | d_i / k_i | 当前有效邻居占自身上限的比例，不是资源利用率 |
| 最大分量比例 | 最大连通分量大小 / n | 图连通程度；始终同时报告分量数与孤立节点数 |
| 广播可靠性 r_b | 第 b 次广播到达的存活节点数 / n，包含源 | 对这次实际广播的覆盖，不是快照图能覆盖的理论范围 |
| 序列平均可靠性 | (1/20)Σ r_b | 先在一个 seed 内对序列取均值，再跨 seed 比较 |
| 应用工作量 M_i | 指定阶段节点 i 的应用发送尝试数 | 包含失败尝试和重复投递；不是 CPU 时间 |
| 归一化工作量 L_i | M_i / (m × c_i) | 每广播平均发送次数相对 capacity 的工作量代理；不能称为实际利用率 |
| 控制开销 Q | 指定阶段控制发送尝试总数 | 与应用发送分开，包含握手与实际启用的 probe |
| 连接变更 | 阶段内 up/down 事件增量 | 动态调整和恢复造成的拓扑扰动 |
| active/passive accuracy | 对应本地视图中存活地址数 / 条目数 | 空视图按现有实现记 1；需与视图占用率一起看 |

可补充归一化工作量的最大值、P95 和 Jain 指数：

\[
J(L)=\frac{(\sum_{i\in V}L_i)^2}{n\sum_{i\in V}L_i^2}.
\]

没有发送工作时该指标记为“不适用”，不要用它制造公平性改善。J 越接近 1 表示 L 分布越接近均等；它只是我们选择的工作量公平性标准，不自动代表整体协议更优。度数与 capacity 的相关性也只能验证拓扑结构，不能单独证明性能收益。

**图性质（graph properties）。**以下结构指标由 `simulation.metrics.graph_properties` 计算，保存在每个测量窗口和故障前 / 后快照的 `graph_properties` 中：

| 图性质 | 定义 | 为什么与容量适应有关 |
|---|---|---|
| capacity–degree Spearman ρ | c 与实际 degree 的秩相关 | RQ1 的单个数字：上限是否真正转化为度数分配；fixed / permuted 应接近 0 |
| 度同配性 r | 边两端 degree 的 Pearson 相关（Newman） | r>0 表示高度节点彼此相连，形成 “rich club”；定向失败时风险集中 |
| 能力组混合比例 | 两端能力组为 (1-1)…(4-4) 的边占比 | 比 r 更直观：高-高边占比多少 |
| 割点数 / 桥数 | 单个节点 / 单条边移除后使其所在分量断开 | “单点故障” 数量；故障后尤其有意义 |
| 割点平均 capacity | 割点的平均 c | 判断结构脆弱性是否落在强节点上 |
| 广播深度 | 每次广播中最后一个首次投递的跳数 | 延迟代理（跳数，不是秒）；度数集中通常缩短路径，但也可能变长 |

路径均值、聚类系数和直径可作为次要指标。图不连通时，路径和直径仅针对最大连通分量；抽样 BFS 的直径值是下界，应保留输出标记。初期不要让昂贵的全图路径计算占据主要实验时间。

异构方案主动让不同节点拥有不同 degree，因此“原始 degree 方差更小”不再是目标。可观察 capacity 与 degree 的对应关系，以及归一化工作量的分布。若需要进一步解释定向失败，可补割点 / 桥数量或节点介数；这些是可选诊断指标，不要求本科主实验全部实现。

一个有用的正确性检查：在静态、连通、可靠的无向图上，首次接收者向除发送者外的邻居转发，则每次完整洪泛的发送数为 2E−n+1。因此同样实际边数下，重新分配 degree 不会自动降低总洪泛发送数。重点是工作由谁承担，以及故障后的覆盖和恢复代价。

## 8. 评估矩阵与阶段

| 阶段 | 设置 | 目的 |
|---|---|---|
| pilot | N=120，seed 0–4，三资源组等比例 | 先核查流程、预算、对照和图形 |
| 稳定比较 | 三方案，同样稳定设置 | RQ1、RQ2 |
| 动态变化 | 同初始图的 static 与 adaptive，成对交换资源 | RQ3 |
| 故障比较 | 三稳定方案；0/20/50/80%；random/top-capacity；20 广播+10 恢复 tick | RQ4 |
| 主实验 | N=120、300、1200；20 个独立 seed | 检查规模影响与跨 seed 稳定性 |
| 敏感性 | 非同比分布、另一 detector；必要时上下限或映射变化 | 检查结论依赖哪些假设 |

已实现的敏感性入口：`--resource-mix decoupled`（CPU/RAM 不同比，c 和 k 不变）与 `--failure-detection connection`。注意 decoupled 在当前 `min` 评分下与 proportional **逐位相同**，因为协议只使用 c；它是“结果只依赖 c”的不变性检查，不是 CPU 与 RAM 作用的区分实验（见 §3.0）。

按阶段推进，不必一开始穷举所有交叉组合。先让一个 pilot 流程可信，再跑主矩阵。当前运行器要求 N≥12 且能被 6 整除，以保证等量资源组和偶数槽位预算；上表的规模均满足。

当前三组 CPU 与 RAM 完全同比增长，无法独立识别哪个资源影响结果。至少增加一组非同比敏感性配置。例如等比例使用 (CPU, RAM GiB)=(2,12)、(8,8)、(8,16)：对应 c 仍为 1、2、4，预算仍为 5N，而这组三点的 CPU/RAM Pearson 相关为 0。这不是宣称资源统计独立，而是避免仅用完全相关输入验证双资源映射。更一般的独立分布可能改变 c 和总预算，须重新报告预算，不能直接沿用“恰好 5N”的说法。

**统计单位是 seed 对应的独立运行。**同一 overlay 的 20 次广播、10 个 tick、多个节点都不是 20 或 10 个独立 seed。跨方案比较可以先对同一 seed 求指标差值，再报告这些差值的均值与区间；展示原始 seed 点。五个 pilot seed 主要用于发现问题，不应给出很强的显著性结论。

## 9. 初始图应该怎样读

| 图 | 横轴 / 纵轴 | 重点检查 |
|---|---|---|
| 资源与连接 | capacity 组 / 实际 degree，区分三方案并显示上限 | 强节点是否接近较高上限；是否存在低占用和孤立节点 |
| 归一化应用工作量 | capacity 组 / M_i/(m × c_i) | static-capacity 是否减轻弱节点负担；permuted-caps 能否排除仅由异构度数造成的效果 |
| 动态调整 | 变化后的 tick / degree 或目标占用率，同时显示连接变更开销 | adaptive 是否朝新资源分配调整，是否付出过多连接扰动；static 是冻结对照 |
| 故障后广播 | 广播序号 1–20 / 可靠性，按失败比例与名单类型分面 | 无周期维护期间如何修复；高能力节点失败是否暴露集中风险 |
| 恢复过程 | tick 0–10 / 最大分量比例、失效条目或累计控制增量 | 明确这是启用 probe 后的恢复，与前 20 广播阶段分开 |
| 图结构（图 4） | 方案 / Spearman ρ、度同配性、割点数、广播深度，每个 seed 一个点 | 上限是否转化为度数；是否形成 rich club 或单点故障 |
| 故障时间过程（图 5） | 广播序号 1–20 与恢复 tick / 覆盖率、最大分量 | 结果如何随时间变化，而非只看平均值 |

**如何测量、仿真并画出“变化”。**所有变化都用同一模式：(1) 在事件前取快照；(2) 注入事件（资源交换或 crash）；(3) 每个广播或每个 tick 记录一行时间序列；(4) 横轴为广播序号或 tick（不是秒），纵轴为指标，跨 seed 取均值并画标准差阴影。事件发生时刻画竖线（tick 0）。这样同一张图能看到下降幅度、恢复速度与是否未恢复。

所有汇总图标明节点数、seed 数、检测模型和失败类型。图中的波动区间以 seed 为单位；配色和坐标范围尽量一致。不要只展示恢复最好的种子，也不要把观察窗口内未恢复的运行删掉。

## 11. 可以得出的结论与边界

可以得出有条件的结论，例如：“在这里定义的 CPU/RAM score、预算及 detector 下，资源匹配降低了弱节点的归一化发送负担，但高能力节点定向失败会损失更多连接。”也可以报告负面结果，例如较高上限难以填满、调整收益小于控制成本，或某些故障下可靠性下降。这些都是有效研究结果。

不能据此宣称：CPU 实测更省、内存消耗更少、真实吞吐更高、检测更快、全网永不分区、算法最优，或已经复现 Gia / HyParView 的原始性能结果。没有带宽模型，也不能将 CPU/RAM score 解释为实际链路能力。

后续扩展可考虑容量相关的消息节流、服务率或 retry 策略，但它们会引入新的负载与调度模型，应作为独立实验。当前版本先保留既有广播失败后的替补尝试，不再增加另一套资源相关 retry 规则。无需为了本科主问题加入真实监控器、异步网络框架、超时模拟或随机丢包。
